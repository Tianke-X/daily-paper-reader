## 摘要
大语言模型（LLMs）在Text-to-SQL系统中的使用日益增多，但SQL错误仍然是实际Text-to-SQL推理流程中的主要障碍。现有的SQL纠正方法要么依赖大规模、高质量的训练数据并产生大量开销，要么采用单路径智能体工作流，这类工作流对早期错误较为脆弱，且容易导致错误传播。为在工业场景中开发实用的SQL正确性系统，我们提出了一种无需训练的框架，将SQL纠正建模为计划引导的树结构调试过程。通过维护多种纠正策略并支持回溯，该框架减轻了迭代细化过程中的错误累积。我们进一步集成了基于执行的验证和子句级诊断工具，以支持策略剪枝和精确错误定位。我们在BIRD-Critic基准上评估了该系统，观察到相较于强LLM基线和代表性基于智能体的基线具有一致的准确性提升，较之前最先进的方法提高了9.42%。该框架还部署在火山引擎的Torch日志服务（TLS）中，以支持在线Text-to-TLS API。在生产环境中，使用代表性强的LLM骨干网络（GPT-5），真实用户查询的执行准确率从36.77%提升至53.61%。这些结果证明了我们方法在实际部署中的有效性和稳定性。

## Abstract
Large Language Models (LLMs) have been increasingly adopted in Text-to-SQL systems, yet SQL errors remain a major obstacle in real-world Text-to-SQL inference pipelines. Existing SQL correction approaches either rely on large-scale, high-quality training data with substantial overhead, or adopt single-path agentic workflows that are brittle to early mistakes and prone to error propagation.   To develop a practical SQL correctness system for industrial scenarios, we present a training-free framework that formulates SQL correction as a plan-guided, tree-structured debugging process. By maintaining multiple correction strategies and enabling backtracking, the framework mitigates error accumulation during iterative refinement. We further integrate execution-based verification and clause-level diagnostic tools to support strategy pruning and precise error localization.   We evaluate the system on the BIRD-Critic benchmark and observe consistent accuracy gains over strong LLM backbones and representative agent-based baselines, achieving a 9.42% improvement over the previous state-of-the-art method. The framework is also deployed in the Torch Log Service (TLS) of Volcano Engine to support an online Text-to-TLS API. In production, it improves execution accuracy from 36.77% to 53.61% on real user queries with a representative strong LLM backbone (GPT-5). These results demonstrate the effectiveness and stability of our approach in real-world deployments.

**现有方法的不足**：
- **训练依赖型方法**：需要大规模高质量标注数据，获取成本高昂，且对多方言泛化能力差（例如 Xiyan 模型在 TLS 方言上准确率仅 13.40%，远低于通用模型 GPT-5 的 36.77%）。

**核心问题**：如何构建一种**无需训练**、能在多样 SQL 方言和工业约束下稳定工作的 SQL 纠错系统，从根本上克服线性修复的脆弱性和不可逆性？

**提出的解决思路**：ACTS-SQL 将 SQL 纠错重新建模为**计划引导的树结构调试过程**，通过分支（branching）保留多个修正策略、通过回溯（backtracking）丢弃错误路径，并结合执行反馈与子句级诊断工具实现精细化的纠错流程。

## 2. 论文提出的方法论

### 2.1 核心思想

将 SQL 纠错从线性、单路径的迭代修复，转变为**树状结构**的调试过程：

- **分支（Branching）**：当用户意图存在歧义或存在多种合理修复策略时，同时保留多条候选路径，避免过早承诺单一假设。
- **回溯（Backtracking）**：当某条路径被验证为错误时，系统回退到之前的节点，探索其他分支，而非继续在错误轨迹上累积修改。

### 2.2 系统架构

系统由 **Central Agent**（中央智能体）和 **Tools**（工具集）两大组件构成。

**Central Agent** 承担三项核心职责：
1. 生成初始的树状修订计划；
2. 在分支点选择最可信的下一步节点；
3. 评估生成的 SQL 候选是否正确，决定继续、回溯或终止。

Central Agent 的 prompt 包含任务说明、可用工具规范、JSON 输出格式约束和完整上下文（用户问题、数据库 schema、问题 SQL、执行历史、计划树状态）。

### 2.3 五个关键工具

| 工具名称 | 类型 | 功能 |
|---|---|---|
| **Detect Ambiguities** | LLM 工具 | 分析用户查询中的歧义表达，为每个歧义项枚举 2–3 种合理的 schema 相关解释，形成树的分支节点 |
| **Inspect Columns** | 执行工具 | 检索指定表/列的样本值，帮助 agent 了解真实数据格式，辅助构造精确匹配谓词 |
| **Run SQL** | 执行工具 | 执行任意 SQL 语句并返回结果，用于验证中间假设和语义假设 |
| **Split and Fix Syntax Error SQL** | 混合工具 | 将语法错误的 SQL 分解为最小可独立执行的子查询（投影、过滤、连接、聚合），并行验证，精确定位语法错误后合成修复版 SQL |
| **Generate SQL** | 混合工具 | 叶子节点工具，基于积累的完整上下文生成修正后的 SQL，并执行验证 |

### 2.4 算法流程（Algorithm 1）

```
1. 根据用户问题 U、初始 SQL S0、数据库 schema D 生成初始修订计划树 T
2. 从根节点开始执行
3. 循环：
   - 执行当前节点对应的工具
   - 若工具是 detect_ambiguities：展开树，生成多个候选子分支
   - 若当前有多个子节点：Central Agent 选择最可信分支继续
   - 若工具是 generate_sql：
       若 SQL 验证通过，返回结果
       否则，回溯到树中任意节点，继续探索
   - 若只有一个子节点，继续向下遍历
```

### 2.5 关键设计要点

- **修订计划树**：每个节点对应一次工具调用，边表示可能的后续动作。计划可动态扩展。
- **验证机制**：SQL 正确性不依赖 LLM 的判断，而是通过真实数据库执行结果进行 grounded 验证。
- **最小化编辑原则**：在 Generate SQL 工具中，LLM 被要求尽量最小化编辑原始查询，禁止投机性假设，修改必须基于已收集的证据。
- **语法修复效率**：通过子句级分解授权并行验证，避免整体重写引入新的语义偏差。

## 6. 论文的主要结论与发现

1. **树状规划显著优于线性细化**：线性计划变体在多个数据集上性能大幅下降（如 Open-PostgreSQL 从 58.70% 降至 45.81%），验证了分支与回溯机制的有效性。
2. **执行反馈至关重要**：去除执行工具后性能降幅最大（Open-PostgreSQL 降至 39.84%），说明数据级验证是可靠分支选择和回溯决策的基础。
3. **歧义检测补充语义纠错能力**：去除歧义检测也造成明显性能回退（Open 子集平均下降 15 个百分点左右），表明显式处理用户意图歧义是语义纠错不可或缺的环节。
4. **ACTS-SQL 在公共基准上达到 SOTA**：BIRD-CRITIC-Open 上达 58.70%（PostgreSQL）、64.29%（MySQL）、53.06%（SQLServer）、33.67%（Oracle），比此前最佳方法（Xiyan 49.28%）高 9.42 个百分点。
5. **在真实工业场景中显著提升端到端准确率**：GPT-5 基座下从 36.77% 提升至 53.61%，GPT-o3 下从 40.55% 提升至 56.36%。
6. **训练方案的方言迁移局限**：Xiyan 等微调模型在 TLS 非标准方言上准确率远低于通用模型，验证了无需训练的方法在多方言场景中的普适性价值。
7. **树状调试能克服线性方法的语义承诺问题**：案例表明，线性方法受困于早期隐含假设（如将"monthly sales"错误理解为年度聚合），树状方法通过分支和回溯能收敛到正确语义。

4. **没有分析失败案例**的定量分布（如仍残留语法错误的比例、语义错误的比例、无法收敛的比例），对系统能力边界刻画不足。

### 方法层面

1. **延迟仍然偏高**：即使非推理模型下的端到端延迟也约为 3 分钟，对于许多在线交互式查询场景可能过长；论文尽管论证了"延迟可接受"，但没有与线上系统的实际 SLA（服务水平协议）约束做严格比较。
2. **API 调用次数和 token 成本随时间变化**：仅以 GPT-o3 报告平均 8,984.5 token，但未报告不同基座之间的成本差异；使用推理模型（GPT-o3/GPT-5）的延迟远超简单方法。
3. **Central Agent 对 LLM 的推理能力依赖较强**：生成合理初始计划、识别关键分支、判断回溯时机都依赖于底层模型的高能力；在小模型上（如 DeepSeek-R1 在 TLS 中增幅仅 1.17%）效果提升有限，这可能意味着框架收益与基座能力存在门槛效应。
4. **没有和专门训练的大规模纠错模型（如训练版的 SQLCritic 等）在同等条件下对比**——对比的 SQLFixAgent 等虽有一些是训练的，但主要是线性范式，而微调的 Xiyan 是面向生成任务而非纠错任务，缺少与**为纠错专门微调且为树状结构设计**的模型对比。
5. **Backtracking 的具体机制描述较粗**：如何从"选择哪个节点回溯"——是否由 LLM 自由选择、是否有启发式规则限制回溯深度或范围，论文未给出足够细节。

### 论文本身的客观性

1. 论文标题中"critic-oriented"与批评导向相关论证主要集中在工具层面（执行反馈 + 验证），未提出独立的"批评者模型"训练或显式的批评打分机制，框架定位与实际实现稍有出入。
2. 论文中部分引用（如 Claude-4、GPT-5 等未来/较新模型）时间标注为 2026 年，在论文评审时段可能需要验证这些模型的实际可用性。
3. 在真实部署中仅报告了准确率提升，未披露对线上用户体验的其他指标（如用户满意度、查询重试率、系统资源占用等）的影响。

### 应用限制

- **数据库实例的可执行性是前提**：框架依赖真实的数据库连接和查询执行能力；在没有可执行环境的场景中（如仅静态 SQL 审核）不适用。
- **临时表和并行执行可能在权限受限的数据库环境中受限**：生产数据库可能不允许创建临时表或执行任意 SQL 子查询。
- **N+1 次 LLM 调用带来的成本**对于大规模批处理（如训练数据清洗）可能造成显著的经济开销。
